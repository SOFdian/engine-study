# 第四周学习计划：Allocator 基础（一）

> 依据《52 周引擎岗学习路线》中的“第 4 周：Allocator 基础一”进行细化。本周标志着从“使用内存”转向“管理内存”，目标是初步构建引擎底层的高性能内存分配基础设施。

------

## 一、 本周目标 🎯

本周的核心任务是**摆脱对标准库 `new/delete` 的依赖**，针对引擎中常见的生命周期场景（如单帧数据、关卡数据）实现确定性高、性能优异的分配器。

围绕原路线要求，本周需要完成以下 4 个结果：

1. **Linear Allocator (线性分配器)**：实现一个极简的“Arena”分配器，支持快速分配与整体重置。
2. **Stack Allocator (栈式分配器)**：在垂直方向扩展分配逻辑，支持 LIFO（后进先出）顺序的局部释放。
3. **对齐分配支持**：确保分配器能够处理内存对齐需求，避免因对齐问题导致的 CPU 性能下降。
4. **性能对比测试**：编写测试用例，对比自定义分配器与 `std::malloc` 的分配耗时差异。

------

## 二、 本周学习原则 💡

### 1. 确定性重于灵活性

通用分配器（如 `malloc`）必须处理复杂的内存碎片，而引擎分配器通常服务于特定生命周期。**不要试图写一个全能的分配器**，而要写一个在特定规则下极快的分配器。

### 2. 图解先行，编码在后

内存分配本质上是原始内存块（`void*`）中指针的位移。在动手实现 `allocate` 逻辑前，**必须在纸上画出内存布局示意图**，标明 `start_ptr`、`current_ptr` 和对齐后的填充字节（Padding）。

### 3. 严格的边界防护

自定义分配器最容易引发内存越界。必须在代码中大量使用 `assert` 检查缓冲区剩余空间，并考虑接入上周学习的 **AddressSanitizer** 进行运行时验证。

#### 今天学什么 📖

### Day 2：线性分配器 (Linear/Arena Allocator)

#### 今天学什么 📖

- **工作原理**：仅维护一个 `offset` 指针，每次分配后向后移动，不支持单独释放。
- **Reset 语义**：一键清除所有已分配数据，极适合单帧渲染数据（Per-frame data）。

#### 今天怎么学 🧪

1. 预分配一块大内存（如 10MB）。
2. 实现 `allocate`：返回当前指针，移动指针。
3. 实现 `clear`：将 `offset` 置零。

#### 今天的产出物 🛠️

- `LinearAllocator` 类实现。
- 单元测试：验证在分配耗尽时的处理行为。

------

### Day 3：内存对齐的数学实现

#### 今天学什么 📖

- **对齐公式推导**：给定地址 *A* 和对齐要求 *L*，计算对齐后的地址 *A*′：

  *A*′=(*A*+*L*−1) & ∼(*L*−1)

- **Padding 填充**：如何处理原始指针与对齐地址之间的差值。

#### 今天怎么学 🧪

1. 手动推算不同对齐要求下的地址偏移。
2. 在分配器中封装 `align_forward` 工具函数。
3. 编写 `static_assert` 验证对齐算法的正确性。

#### 今天的产出物 🛠️

- 通用内存对齐工具库（位于 `engine_core/math` 或 `tools`）。

------

### Day 4：栈式分配器 (Stack Allocator)

#### 今天学什么 📖

- **工作原理**：支持 LIFO 模式释放。释放时检查是否为最后一次分配的对象。
- **Header 设计**：每个分配块前是否需要存储元数据（如 Padding 大小）以便回退。

#### 今天怎么学 🧪

1. 记录分配时的 Marker（当前偏移量）。
2. 实现 `free_to_marker`：将指针回退到指定位置。
3. 对比 Stack 与 Linear 的灵活性差异。

#### 今天的产出物 🛠️

- `StackAllocator` 类实现。

## 五、 给你的执行建议 💡

1. **不要过度抽象**：在这一阶段，优先保证逻辑正确。不需要引入过于复杂的 C++ 模板技巧（如 `std::allocator` 兼容接口），先跑通简单的 `void* allocate(size_t)` 即可。
2. **可视化内存**：调试时，可以使用 `printf("%p")` 打印地址，观察地址是否符合对齐规律（例如最后几位是否为 0）。
3. **关于释放**：注意 `LinearAllocator` 本周是不支持 `deallocate` 的，这属于正常设计，不要试图在这里加入复杂的内存回收逻辑。
